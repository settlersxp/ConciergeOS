# Client Backend — Dummy Service-to-Service Client

A minimal FastAPI backend that demonstrates how a second client can authenticate against the same Keycloak realm using the **Client Credentials Grant** flow and then call the main backend's API securely.

## Purpose

This project is a learning tool that shows:

1. **Multiple OIDC clients** can coexist in the same Keycloak realm
2. **Client Credentials Grant** — machine-to-machine authentication (no user involved)
3. **Each client has its own `client_id` + `client_secret`** — credentials are isolated
4. **Caddy routes traffic** to different backends over the same domain
5. **Service-to-service calls** using OAuth2 access tokens

## Architecture

```
Browser
  │
  ▼
┌─────────────────────────────────────────────────────┐
│  Caddy (out-customer.com)                           │
│                                                     │
│  /api/*        ──▶  backend:8000                    │
│  /client-api/* ──▶  client-backend:8000             │
│  /auth/*       ──▶  keycloak:8080                   │
└─────────────────────────────────────────────────────┘
                      │
                      ▼
              ┌───────────────┐
              │   Keycloak    │
              │               │
              │  Clients:     │
              │  - concierge  │  (existing, PKCE + oauth2-proxy)
              │  - client-api │  (this service, Client Credentials)
              └───────────────┘
```

## Endpoints

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/client-api/health` | Service health check |
| `GET` | `/client-api/token-info` | Acquire OAuth2 token + decode/inspect JWT payload |
| `POST` | `/client-api/refresh-token` | Force token refresh (re-authenticate with Keycloak) |
| `GET` | `/client-api/backend/health` | Call the main backend's `/` endpoint |
| `GET` | `/client-api/backend/models` | Call the main backend's `/api/models` with Bearer token |
| `GET` | `/client-api/backend/settings` | Call the main backend's `/api/settings` with Bearer token |
| `POST` | `/client-api/backend/post/*` | Generic POST proxy to any backend endpoint with Bearer auth |

## Running

```bash
# 1. Ensure Keycloak is running and the client-api client is created
cd docker && docker compose up -d keycloak backend
python keycloak_setup.py localhost 8080

# 2. Start everything (including client-backend)
docker compose up -d

# 3. Test the endpoints
curl -k https://out-customer.com/client-api/health
curl -k https://out-customer.com/client-api/token-info
curl -k https://out-customer.com/client-api/backend/models

# Locally (outside Docker)
pip install fastapi uvicorn httpx
CLIENT_API_CLIENT_ID=client-api CLIENT_API_CLIENT_SECRET=xxx \
KEYCLOAK_URL=http://localhost:8080/auth KEYCLOAK_REALM=production \
BACKEND_URL=http://localhost:8000 \
uvicorn client_backend.main:app --host 0.0.0.0 --port 9000
```

## Environment Variables

| Variable | Default | Description |
|----------|---------|-------------|
| `KEYCLOAK_URL` | `http://keycloak:8080/auth` | Keycloak base URL |
| `KEYCLOAK_REALM` | `production` | Keycloak realm |
| `CLIENT_API_CLIENT_ID` | `client-api` | OAuth2 client_id for this service |
| `CLIENT_API_CLIENT_SECRET` | *(required)* | OAuth2 client_secret (generated by `keycloak_setup.py`) |
| `BACKEND_URL` | `http://backend:8000` | Main backend internal URL |

> **Note:** The service only needs its own `CLIENT_API_CLIENT_ID` + `CLIENT_API_CLIENT_SECRET`
> credentials to authenticate with Keycloak (Client Credentials Grant) — no admin credentials required.

## How it works

### OAuth2 Client Credentials Grant Flow

```
  ┌──────────────────┐         ┌──────────────┐
  │  client-backend  │         │   Keycloak   │
  │                  │  POST   │              │
  │  1. Request token │──────▶│  /token       │
  │  (client_id+     │        │              │
  │   client_secret) │        │              │
  │                  │◀──────│              │
  │  2. Receive JWT  │  200   │              │
  └────────┬─────────┘        └──────────────┘
           │
           │  3. Call backend with Bearer token
           │  GET /api/models
           │  Authorization: Bearer <JWT>
           │
           ▼
  ┌──────────────────┐
  │   backend        │
  │   (FastAPI)      │
  └──────────────────┘
```

1. **Acquire token:** The service presents its `client_id` + `client_secret` to Keycloak's token endpoint.
2. **Receive JWT:** Keycloak validates the credentials and returns a JWT access token.
3. **Call backend:** The service attaches the token as `Authorization: Bearer <token>` when calling the main backend.

### Example: Inspect the token payload

```bash
curl -k https://out-customer.com/client-api/token-info
```

Response:

```json
{
  "status": "valid",
  "token_type": "Bearer",
  "expires_in": 300,
  "expired": false,
  "scope": "openid",
  "payload": {
    "exp": 1790000000,
    "iat": 1790000000,
    "iss": "https://out-customer.com/auth/realms/production",
    "aud": [
      "account",
      "concierge"
    ],
    "azp": "client-api",
    "client_id": "client-api",
    "username": "service-account-client-api",
    "typ": "Bearer",
    "auth_time": 1790000000,
    "session_state": "...",
    "realm_access": {
      "roles": [
        "default-roles-production",
        "offline_access",
        "uma_authorization"
      ]
    }
  }
}
```

> **Notice:** The `azp` (authorized party) and `client_id` fields are set to
> `client-api` (this service's client), distinguishing it from the `concierge`
> client used by oauth2-proxy. Each client in Keycloak has its own identity
> and credentials, enabling independent management and auditing.

### Example: Call backend with authenticated token

```bash
curl -k https://out-customer.com/client-api/backend/models
```

The client-backend will:
1. Check if the cached token is still valid.
2. If expired (or not cached), authenticate with Keycloak (Client Credentials Grant).
3. Call `http://backend:8000/api/models` with `Authorization: Bearer <new_token>`.
4. Return the result.

## Key Concepts Demonstrated

| Concept | Description |
|---------|-------------|
| **Multiple clients** | `concierge` (user-facing) and `client-api` (machine-to-machine) coexist in the same Keycloak realm |
| **Credential isolation** | Each client has its own `client_secret` — compromising one doesn't affect the other |
| **Grant types** | `concierge` uses Authorization Code + PKCE (user flow); `client-api` uses Client Credentials (machine flow) |
| **Token-based auth** | The client-backend gets a JWT from Keycloak and uses it to authenticate to the backend |
| **Token caching** | The JWT is cached and automatically refreshed when it expires |
| **Caddy routing** | Caddy directs `/client-api/*` traffic to the client-backend, separate from `/api/*` to the main backend |
